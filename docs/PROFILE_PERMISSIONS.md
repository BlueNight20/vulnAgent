# 审计档案、工具权限与审批路径

Linux 审计档案使用 verifier 角色，与现有命令工具的审批权限一致。之前该档案使用 analysis，默认角色规则没有授权任何所列命令工具，导致工具虽然在目录中却无法执行。verification 档案现包含命令/模块工具，以便在确有访问依据时安排独立复核；目录没有的工具不会被补造。

Worker 启动选择工具时，按档案声明及显式建议，从已同步 MCP 目录选择，再过滤当前任务和全局的角色权限。显式建议也不能越过角色权限。需审批的工具可以向模型展示，用于提交审批申请；并不在批准前执行。执行及审批重放仍独立查询最新授权范围、角色权限、参数 Schema 和预算，因此运行中收紧权限会阻止旧工具定义继续使用。

同一角色、工具匹配的全局及当前任务规则共同参与判断：至少一条 allowed=true 且没有匹配的 allowed=false 才授权。**显式拒绝优先**，规则顺序不影响结果；无匹配默认拒绝。任一匹配授权要求审批即保留审批，目录标记 destructive 也要求审批。要解除拒绝，须修改相应拒绝规则，新增一条授权不能覆盖它。兄弟任务规则不参与本任务。

默认命令工具 run_shell_command / run_kali_tool / msf_console_execute / msf_run_module 均有 verifier 角色审批规则。新空权限库还会初始化 verifier 的 msf_search / msf_module_info 查询权限。已有权限库保持用户设置，不自动补加或覆盖默认规则；若这些查询未获授权，应通过权限配置显式调整。仅有目录和档案声明不构成执行授权。

Worker 工具结果 details.toolCallId 现在返回实际持久化调用 ID，与审批页和证据追踪一致；缺少持久化记录时才保留 SDK 调用 ID。此前待审批结果的文字给出真实 ID，details 却给出模型调用 ID，不能用于查找审批记录。

命令工具的执行位置由 MCP 实现决定；本系统不会把执行机本地的 id、权限或系统信息自动当作靶机结果。Linux 审计与 verification 提示词要求已有可追溯的远程访问/会话、实际 Schema 支持和目标身份依据。缺少条件时保留阻塞或无法确认。系统不会创建远程凭据、臆造会话或修改 blhackbox。工具侧如何绑定会话和远端主机，仍须由操作者在实际目录及授权靶机上确认。

`npm run test:profile-permissions` 使用迁移内存 SQLite、真实 Worker 工具定义、执行器、审批服务和独立验证服务。固定工厂返回文本，不运行命令、不连接工具或目标。覆盖 Linux 角色、目录/权限交集、任务拒绝与兄弟任务隔离、显式建议不能放权、批准前零调用、批准后撤权阻止重放、恢复权限后同参数仍须审批并产生独立新调用/新证据，以及范围外拒绝。该验证证明协议和状态接线，不证明真实权限获取或提权效果。
