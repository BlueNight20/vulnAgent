# Worker 并发与新任务默认值

更新：2026-11-03。适用于当前单 API 实例、SQLite 版本。

## 配置含义

设置页的“全局 Worker 并发上限”限制所有任务合计的 Worker 执行分配，派发排队 queued 和运行中 running 都占名额。每个任务的 workerCount 仍是自身上限；两者同时满足才能派发。Planner 不占 Worker 名额，但 Planner 与 Worker 的模型请求共同受模型并发上限限制。

修改全局上限后，下次占位读取当前数据库设置；没有保存值时读取 WORKER_MAX_CONCURRENCY，默认 2。降低上限不强制终止已分配的 Worker，因此界面可能暂时显示占用数高于新上限；继续等待收尾，不再新增名额。暂停保留已有 Worker 分配，停止/完成/失败收尾后释放。该上限管理应用内分配，不证明外部 MCP 进程已经退出；远端取消仍须核实。

派发在同一数据库事务中核对任务、意图状态、全局/任务占用及重试次数，再同时创建 Worker 占位和更新意图。竞争未拿到名额时不创建 Worker、不改派发数或重试数；事务失败不留下半个占位。通知在提交后发送。

等待期间显示“等待 Worker 并发槽位”，每 5 秒通过巡检继续调度，不消耗无进展轮次或额外重试；时间预算仍继续计算。没有跨任务严格 FIFO 公平性保证。队列租约过期会回收，启动失败也会清理会话和释放名额。旧心跳、迟到绑定或完成不能复活 timeout / cancelled 等终态。

## 新任务初始化

每次打开新任务抽屉先重新读取系统设置，再初始化模型、默认 Token / 时间预算及默认 Worker 数量。不会先使用旧缓存创建任务；读取失败显示错误并允许重试，不静默改用硬编码值。

模型选择使用保存的真实模型名，也可显式选择预设型号；不再发送 custom 占位名。已填写的草稿不随后台设置刷新被覆盖，关闭后重新打开才重新初始化。任务请求显式保存选择的模型、预算和数量；API 直接创建任务仍须提供这些字段，不把缺失字段当作表单默认值。默认预算范围与任务一致：Token 1000～10000000，时间 1～1440 分钟，Worker 1～8。

执行引擎关闭时，新任务默认不自动启动；用户可以先保存待启动任务，再开启并手动启动。新任务自身上限可以高于全局值，实际并发仍由全局占位控制。

## 重启与恢复

启动对账把遗留 queued / running Worker 标记为中断历史，并对账 created / running / paused 会话；不自动重放工具。中断的运行任务暂停等待人工核实后恢复。已收尾 Worker 的旧会话不能通过智能体页单独恢复，暂停任务也须先恢复任务引擎，避免绕过占位与生命周期。

## 验证

`npm run test:worker-capacity` 使用真实迁移的临时文件库、实际设置/任务/意图/Worker/编排服务，多个服务实例并发申请 12 个名额。覆盖全局/任务上限、实时升降、等待不消耗尝试、同意图竞争、插入/更新/提交故障、无效配置、排队租约回收及终态保护、真实循环等待/唤醒/时间预算、准备/启动失败释放、启动中暂停、真实 WorkerRunner 的会话清理、旧会话恢复约束及真实文件库重新打开后的人工恢复状态。

界面测试覆盖保存模型/默认预算/数量、草稿保留、重新打开后新配置优先于缓存、读取失败不使用旧缓存并可重试。真实入口的独立固定模型/MCP 协议测试继续验证实际 SDK、并行 Worker、证据、复核、报告与中断恢复。所有开发验证都不访问靶机，也不等同真实测试效果评估。
